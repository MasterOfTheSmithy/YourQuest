# YourQuest LLM model and latency audit for 8 GB GPUs

Historical research snapshot, written before inference. The completed [live test report](C:/Users/Garri/YourQuest/Docs/LLM_8GB_Live_Test_Report_2026-10-07.md) now supplies measured results and updated recommendations. Untested candidates below remain unqualified.

7 October 2026. Target: an 8 GB GPU shared with Unity, while preserving general reasoning, character roleplay, and structured proposals reconstructed from canonical world and player context.

The best first experiment is to keep the main GPU model resident through CPU helper requests. The current implementation unnecessarily releases it on that transition. Next, address foreground requests waiting behind already-running background generation. These changes can improve every model without changing accepted content or save ownership. The strongest initial model experiments are stock Qwen3.5 with MTP, official Spark, official LFM2.5, and SmallThinker as a CPU helper. OpenJev is a conditional selector experiment; placing it before every request would introduce another prompt-processing and residency cost.

Priorities below mean **A: test first**, **B: useful second round**, **C: conditional or substantial integration**, **Control: retain for comparison**, and **Hold: resolve the stated evidence gap first**. These are test priorities, not production qualification. No candidate has been newly benchmarked in YourQuest for this audit.

## Current implementation and latency costs

The current configuration uses Qwen3.5-4B Q4_K_M through llama.cpp for control and structured generation, MiniFantasy through Ollama for dialogue, yourquest-qwopus-q4km for Goddess speech, and small-test for summaries. The main server has a 12,288-token context, one slot, flash attention enabled, a 768 MB GPU headroom allowance, and a 45-second idle timeout. Prompt reuse is deliberately disabled under the responsiveness policy. Thinking controls and schema-constrained output already exist. [Current configuration](C:/Users/Garri/YourQuest/Assets/Assets/Scripts/LLM/LLMRuntimeConfig.cs), [request transport](C:/Users/Garri/YourQuest/Assets/Assets/Scripts/LLM/LLMClient.cs:1703).

The queue has priority ordering and burst fairness, but it waits for the active request to finish before dispatching another. A short player-facing request can therefore wait behind a long background call. Consecutive calls to the same resident model already stay warm; the implementation does not unload after every request. [Queue worker](C:/Users/Garri/YourQuest/Assets/Assets/Scripts/LLM/LLMClient.cs:835), [dequeue policy](C:/Users/Garri/YourQuest/Assets/Assets/Scripts/LLM/LLMClient.cs:878).

The residency policy stops GPU llama.cpp when routing to Ollama even when the Ollama request is placed entirely on the CPU. The reverse transition releases the helper. This is the clearest source-level repair opportunity. Acknowledged unloading remains appropriate when two GPU workloads cannot fit together. Ollama currently allows one loaded model and one parallel request; keeping one CPU Ollama model alongside one separate GPU llama.cpp process does not require increasing that limit. [Residency transitions](C:/Users/Garri/YourQuest/Assets/Assets/Scripts/LLM/LLMClient.cs:1371), [release acknowledgement](C:/Users/Garri/YourQuest/Assets/Assets/Scripts/LLM/LLMClient.cs:1429), [Ollama process](C:/Users/Garri/YourQuest/Assets/Assets/Scripts/LLM/OllamaServerProcess.cs).

The GPU fitting calculation recognizes the approved 32-block Qwen model and its exact default filename. It cannot be carried over unchanged to Spark, Ling, SmallThinker, Gemma, or an arbitrary community quantization. The owned server reports build 10516, commit b95502ba9. Its help includes draft-mtp, draft-dspark, and several ngram modes; a listed option does not establish that a particular model works correctly or runs faster. [Server ownership and fitting](C:/Users/Garri/YourQuest/Assets/Assets/Scripts/LLM/LlamaCppServerProcess.cs:203).

Report time to the first visible dialogue token separately from time to a complete accepted structured proposal. Faster token generation can lose overall if a model produces longer reasoning, fails reconstruction, or needs more retries.

## A better multi-model lifecycle

The current serial lifecycle is reasonable when only one GPU model can fit, but model identity should not be the sole residency rule. Within the existing scheduler, use these transitions:

| Requested transition | Proposed behavior |
| --- | --- |
| Same model, unchanged backend | Reuse the resident model and applicable validated prompt prefix. |
| Main GPU model to CPU-only helper | Keep the main model loaded when the current game memory budget permits it. Run the helper under the existing CPU responsiveness budget. |
| CPU helper to main GPU model | Reuse the main model. Retain the helper only if measured RAM and the idle policy permit it. |
| CPU helper A to CPU helper B | With the current one-model Ollama limit, replace the CPU helper only; avoid an unrelated GPU teardown. |
| GPU model A to GPU model B | If measured combined weights, caches, buffers, and Unity peaks do not fit, release A, await acknowledgement, then load B. |
| Background request to new foreground request | Queue priority alone cannot help the active call. Use bounded complete work, safe cancellation of obsolete work, or a qualified same-model second slot. |

Begin with residency repair and one active request. Concurrent CPU/GPU inference is a separate experiment because both can consume CPU and memory bandwidth. The 768 MB headroom setting is an existing policy, not proof that every gameplay scene has enough reserve. Admission must use representative peak gameplay measurements, including transitions and temporary overlap.

The long-term choice should be the simplest configuration that passes all roles: one qualified resident model if possible; otherwise a main GPU model plus one warm CPU helper; then additional GPU models only when measured memory permits them. Persistent server processes and smart batching help lifecycle costs, while stronger foreground scheduling addresses a different source of delay.

## OpenJev as an orchestrator

OpenJev's useful contract is selecting one label from 2–16 supplied choices. Its native runtime offers 16-layer and 32-layer modes, but the inspected GGUF exports use the complete 32-layer model. The official conversion excludes MTP weights. Native early exit therefore cannot be assumed for the supplied Ollama/llama.cpp packages. Thinking must be disabled, and the existing application JSON response contract would need a typed adapter for OpenJev's label. [Official GGUF contract](https://huggingface.co/apus-ailab/APUS-OpenJev-v1-4B-GGUF), [native runtime](https://huggingface.co/apus-ailab/APUS-OpenJev-v1-4B).

For YourQuest, a useful experiment would supply a short relevant state summary and allowed choices such as dialogue, quest proposal, state proposal, clarification, or deeper reasoning. Existing C# owners validate the choice, dispatch work, and control acceptance. OpenJev must not acquire scheduling, mutation, or save authority. Known request types should continue to route directly without an extra LLM call.

Its one-token answer still requires reading the input. A GPU-resident Q4 selector plus the current Q4 target would consume roughly 5.4 GB of weight files before both caches, working buffers, and Unity. Start with offline classification trials or a bounded CPU selector rather than assuming both GPU models fit. Published label probabilities are not calibrated correctness guarantees and should not bypass validation.

If selection proves useful, the native 16-layer low mode is a separate backend experiment. It may reduce selector computation, but it needs its own integration, quality comparison, and memory measurements; it is not enabled by choosing one of the supplied GGUF files.

The break-even criterion is:

**selector loading + selector prompt processing + selection + extra transitions + expected routing-error cost < generation and repair work avoided.**

Compare deterministic routing, no selector, and OpenJev on the same ambiguous cases. Record wrong-lane selections and total accepted-result latency. A selector that improves classification but increases the player's wait fails the latency objective. The two linked GGUF repositories are packaging alternatives for the same family, not two orchestrators to chain together.

## Qualification cases and measurements

Use frozen copies of canonical input documents and existing accepted contracts. Keep this benchmark detached from production saves; model responses remain proposals. Record the model revision, file hash, template, quantization, backend commit, placement, context allowance, sampling settings, and thinking/output budgets in every receipt. Do not compare a GPU model to an accidentally CPU-spilled challenger and attribute the difference to intelligence or architecture.

Start with five distinct fixtures in each of these eight groups, for 40 semantic cases per surviving candidate:

| Case group | What must survive |
| --- | --- |
| World/player JSON reconstruction | Stable IDs, ownership, required fields, enums, relevant facts, and unchanged unrelated state. |
| Contradictory and incomplete context | Resolve authority correctly; request clarification or reject an invalid proposal when needed. |
| NPC memory and dialogue | Character voice, relationship continuity, known facts, recent events, and no invented memories. |
| Fantasy roleplay | Distinct personalities, scene continuity, concise useful replies, and resistance to repetitive generic prose. |
| Quest proposals | Supported objective types, viable conditions, explicit mechanics, rewards, and completion determined by records rather than prose. |
| Goddess narration and summaries | Good transient voice and faithful compression without turning prose into persistent authority. |
| Long context | Put relevant facts near the beginning, middle, and end: include roughly 6K prompts and cases near the 12K total-context allowance, leaving enough space for the required response. |
| Invalid or misleading content | Preserve the untrusted-content boundary and do not execute generated instructions, IDs, or paths. |

First perform a small matched screening subset to eliminate incompatible templates and obvious semantic failures. Then run the full cases only for survivors. Use multiple blind roleplay comparisons against MiniFantasy and matched reasoning comparisons against the current Qwen target. Compare first-pass schema acceptance, semantic acceptance, contradictions, required-fact omissions, unsupported mechanics, and retry counts. A syntactically valid JSON document alone is not a quality pass.

For performance, collect repeated cold, warm, and alternating-role runs. Include short and long outputs, MTP off/on where applicable, and both actual production sampling and a deterministic diagnostic setting. Report median and p95 with the sample count, plus queue time, load/unload time, prompt tokens and processing speed, visible and hidden generated tokens, output speed, complete valid-result time, peak VRAM/RAM, CPU use, and Unity frame time. Repeat foreground interruption scenarios after changing scheduling. A single tokens-per-second screenshot cannot establish the result.

Accept a candidate only if it meets the existing contracts and at least matches the relevant current model on essential reasoning, reconstruction, and voice quality, while improving useful latency or memory behavior. A critical canonical-state violation is a failed fixture even if normalization could silently mask it. Preserve existing rejection and repair evidence rather than weakening the gate to improve acceptance statistics.

## Recommended experiment order

1. Establish the current Qwen, MiniFantasy, Goddess, and summary controls under warm/cold transitions and representative Unity GPU occupancy. Separate CPU spill, loading, active queue blocking, prompt processing, and output length.
2. Repair CPU/GPU residency transitions within LLMClient, then repeat the same controls. Test a bounded cache separately so gains remain attributable.
3. Compare stock Qwen3.5 MTP off/on. Test foreground scheduling independently, then qualify any parallel-slot and MTP combination against the exact backend build.
4. Compare official Spark Q4 and official LFM QAD/Q6 as general-model challengers. Prepare compatible backend builds in an isolated benchmark configuration; do not replace the production binary just to run screening.
5. Compare SmallThinker ordinary GGUF, Qwen3.5-2B, and the current CPU helper. Evaluate PowerInfer only after SmallThinker's semantic and voice quality justify the additional integration.
6. Test Gemma E2B QAT, Ministral, and official non-thinking Qwen3-2507. If Gemma passes, compare its assistant and LiteRT-LM mobile format as separate engine/quantization experiments.
7. Use the voice and reasoning specialists only to address demonstrated weaknesses: DavidAU LFM, Spark FIT, the two distinct Heretic targets, Jackrong, Qwen2507 ablation, Parable, Deckard, and Kimi Luna. Ling needs its own memory/support experiment; Hivemind needs source evidence first.
8. Test OpenJev only on cases where simpler routing wastes measurable generation or repair work. Evaluate its net benefit before placing it in an interactive path.

This ordering keeps quality controls intact while separating lifecycle, model, quantization, and backend effects. The complete list is larger than the first test batch because not every interesting model deserves equal integration effort.
