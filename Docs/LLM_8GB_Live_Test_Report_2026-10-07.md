# YourQuest 8 GB LLM live test results

7 October 2026. The strongest demonstrated repair is to retain the main GPU model through verified CPU-only helper calls and reuse stable prompt prefixes. Both improve the existing pipeline without selecting a weaker replacement. No tested model qualified across reasoning, exact state reconstruction, and character delivery.

The campaign recorded **470 chat cases across 15 models**, **8 OpenJev choice cases**, and **6 additional CPU helper calls inside residency cycles**. Astra independently reviewed **147 blinded voice responses**: 51 passed factual/inquiry hard gates and 42 also passed the delivery screen. These totals span different conditions; they are not a pooled model ranking.

All tests were detached. Unity remained closed, and production code, model settings, accepted saves, world/player authority and imported assets were unchanged. The reserved-memory experiment is a placement diagnostic, not a gameplay or frame-time result.

**The queue and residency repair**

The existing queue already serializes requests and keeps consecutive calls to the same model warm. It does not close the model after every request. The avoidable cost is at a backend transition: [PrepareRoutedModelResidency](C:/Users/Garri/YourQuest/Assets/Assets/Scripts/LLM/LLMClient.cs:1371) closes owned GPU llama.cpp for an Ollama route, and releases the Ollama helper on the return transition, even when that helper uses no GPU.

The concrete proposal is to resolve effective placement before the residency decision, retain one admitted CPU helper alongside the GPU main, verify the helper's actual zero-VRAM placement, and preserve the existing single queue, idle policy, cancellation, lease release, aliases and process ownership. Apply a measured RAM budget and fall back to the acknowledged unload sequence when placement is unknown, changes to GPU, or either budget cannot fit. Switching competing GPU targets still needs a memory-safe handoff.

The CPU rule is conditional: [ApplyOllamaLivePresentationPolicy](C:/Users/Garri/YourQuest/Assets/Assets/Scripts/LLM/LLMClient.cs:1789) respects explicit `num_gpu`, including automatic placement. Backend name alone cannot establish CPU residency. The live retention receipt proves only the existing 1.2B helper combination.

For caching, preserve the zero host snapshot cache and one slot, and add a bounded policy for exact stable prefixes. Do not disable the entire responsiveness policy just to change [cache_prompt](C:/Users/Garri/YourQuest/Assets/Assets/Scripts/LLM/LLMClient.cs:1703). Model/template/schema and player/world identity or revision changes must preserve the proper context. The measured cache behavior saved prompt processing, not generation time.

Priority/fairness cannot interrupt an already-running background request. Bounding obsolete background work, cancellation and continuous batching remain later experiments; queue delay, preemption, multiple slots and frame time were not tested in this campaign. No second scheduler or generated-state owner is proposed.

**Protocol and limits**

The RTX 5060 reported 8,151 MiB, with 8 physical CPU cores and about 32 GiB RAM. Main tests used isolated llama.cpp b10828/3ad1ba733, one slot, four CPU threads, flash attention, batch 128 and ubatch 32, with the required 12,288-token context. Residency used the unchanged production b10516/b95502ba9 engine. Spark startup worked on the benchmark build; the installed production Ollama version is below Spark's published requirement. Runtime installation was isolated under E:/GPT LLM TEST/Runtime/b10828-cuda13.3.

Known-answer fixtures covered zero/unknown preservation, contradictory archives, cross-profile injection, long stale history, an exact route ID/deadline/budget, and event-counter arithmetic. This is a small task-relevant reasoning screen, not an exhaustive general-intelligence benchmark. Most conditions have one or two samples, with specified seeds. The extended-budget phase used published LFM sampling; non-LFM models in that early phase retained standardized sampling. Later capped phases explicitly recorded published-family parameters, applied to the actual weights. Do not read the phase name “native” as proof that every early model used all publisher defaults.

The initial short screen retained stop reasons but not the terminal SSE DONE marker. Its golden counts therefore describe content, not complete strict transport evidence. Later strict audits required the recorded DONE/stop evidence, unique JSON keys, schema and exact golden values. Fast empty or truncated output is a failure, not an accepted-result latency. One initial server-readiness timeout and the NEO template errors remain in the receipts.

GPU/RSS sampling at one-second intervals can miss brief peaks; compare GPU deltas against each server's recorded baseline rather than unrelated desktop totals. Reserved headroom was unallocated space requested from the fitter, not real Unity memory contention. No Play Mode, FPS, concurrent inference, queue-wait measurement, sustained stress, live profile mutation or ordinary player-flow qualification was performed.

The initial 50 Goddess proposals all passed envelope/source prose checks, but only 19 delivered under blinded factual/inquiry/voice screening. Valid factKeys did not establish sentence truth. Final compact and NPC repeats exposed non-answering, reasoning leakage, awkward voice and invented facts. The current speech/verification qualification flags were not enabled or changed.

**Next implementation priority and remaining candidates**

Implement and verify the bounded residency policy first, then independently qualify same-slot prefix reuse. Keep current Qwen as the baseline and the existing generation → typed parsing → validation → normalization → curation → persistence → deterministic runtime boundaries. Test inline MTP only on its exact compatible weights, with sampled behavior checked separately. Gemma and native LFM QAD remain targeted qualification candidates; no universal model consolidation is justified.

The [full research audit](C:/Users/Garri/YourQuest/Docs/LLM_8GB_Model_Method_Audit_2026-10-07.md) retains every supplied link and prior candidate, including Ling, Jackrong, PJRM, Parable, Qwen2507, Hivemind, Qwen3.5-2B, Ministral and Gemma E4B. Those are untested here. Hivemind and the supplied HelpingAI2-6B Q2 file have local fingerprints but no matched publisher provenance; the latter declares only 8K native context. The previously inventoried second Spark filename was absent at the later check; this task did not remove it. These extras were not scored as new qualified models.

DSpark, Gemma assistants, ngram speculation, PowerInfer, LiteRT-LM, adapters, two slots and alternative compiled backends remain untested. Further engine installation is not the first repair supported by these results.
